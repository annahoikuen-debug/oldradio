# Best-Worst 人間評価の手順書（提案⑨-3）

**これは人手が必要なので CI には載せない。**
自動指標（`eval/metrics/`）が測れないもの——「その年にお生まれの方が、素直に頷くか」
——を測るためのものである。

---

## 0. なぜ Best-Worst なのか

- 通常の 5 段階評定は評価者ごとの尺度が大きくずれる（Kreutzer et al. 2020）。
  同じ原稿でも「4」と「5」を分裂して出す。
- Best-Worst は「最も良い」「最も悪い」を **1 つずつ選ぶだけ**の手法である。
  全対全比较を避け、少ない比較者数でも順位が安定する（Zhao et al. 2019）。
- 介護職員 2〜3 名でも**順位**は読める。**絶対値**は読めない。

したがって本手順書は**絶対評定を一切しない**。すべて相対比較にする。

---

## 1. 評価者

| 項目 | 内容 |
|---|---|
| 人数 | **介護職員 2〜3 名**（回想法レクの実際担当者） |
| 適格性 | 週 1 回以上、本アプリの回想法副产品を利用している |
| 報酬 | **有償**。評価は労働である。無償なら「作業」になる |
| 期間 | 月 1 回、1 回あたり 45〜60 分 |

> **施設への説明**: この評価は**アプリの品質を測るためのもの**であって、
> 施設やご家族を評価するものではない。結果を施設に共有しない場合にも、
> 共有する場合にも `docs/model_card.md` の「非対応」を併せて説明する。

---

## 2. ルーブリック（事前に固定・共有・訓練する）

Kreutzer et al. (2020) の指摘に従い、**評価中にルーブリックを変えない**。
変えたい場合は**次の回から**使い直す。

### 3 軸

| # | 軸 | 問い | 判定 |
|---|---|---|---|
| 1 | **懐かしさの自然さ** | その年にお生まれの方が「そうだ」と頷くか？ | Best / Worst（相対） |
| 2 | **対話を促す具体性** | 聞き返したくなる具体的な往事（商品名・番組名・場所）が 1 つでも出そうか？ | Best / Worst（相対） |
| 3 | **誤りの有無** | 「これは違う」と感じる事実が**ある**か？ | **Yes / No（ゲート）** |

### 軸 3 をゲートにする理由

選択肢が 2 つだけなので、すべての判断が効く。5 段階では評価者が
中間点を選ぶことで判断を回避できてしまう。**Yes が 1 つでもあれば、
その候補は最悪の候補から外せない。**

### 「誤り」と判定する条件

- 対象年より後の年・年代表記が出ている（例: 1975 年の原稿に「1980 年」）。
- その年に放送されていない番組を断定している。
- 実在しない曲名・番組名を断定している。
- 体調・治療・薬に関する助言になっている。

**これ以外の表現の不 naturalist さは No。** 日本語が完璧である必要はない。

## 3. 刺激の作り方

1. **対象年を選ぶ。** 24 ケース（`eval/cases/case_defs.json`）から
   **ランダムに 10 ケース**を選ぶ（`care_recreation` モードに絞る）。
2. **各ケースで候補 2 個を用意する。**
   - 候補 A: 現行のプロンプト（ベースライン）
   - 候補 B: 変更後のプロンプト
   - A と B を識別できるラベルで見せない。**提示順をケースごとに反転する。**
3. 候補のテキストは `python -m eval --out eval/results/YYYYMM_raw.json` から
   抜き出す。**数値指標は評価者に見せない**（Best-Worst は順序だけを見る）。

### 提示用紙（1 ケース分）

```
【ケース 3】 対象年: 1975年

<A> と <B> を読み上げて、選んでください。

  A: （原稿の全文）
  B: （原稿の全文）

  最も自然な方（懐かしさが自然）      :  A / B
  最も具体的な方（対話を促す）        :  A / B
  どちらかに事実の誤りがあるか        :  A / B / どちらにもない
```

- 「最も良い方」「最も悪い方」を**両方**聞き、答えが矛盾しないことを確認する
  （同じ方を 2 軸で選ぶのは正常）。
- 順序効果を避けるため、**ケースごとに提示順を反転する**
  （ケース 1 は A→B、ケース 2 は B→A、以下同様）。

---

## 4. 訓練（最初に 1 回だけ）

1. **説明セッション 30 分**
   - 3 軸のルーブリックを読み上げ、意味を共有する。
   - `docs/model_card.md` の「非対応」を読み、「誤り」の定義を共有する。
2. **合同で 2 ケースを評価（15 分）**
   - 評価者全員がそれぞれ独立に選ぶ。**この時点では合意しない。**
3. **差分の説明（15 分）**
   - 選んだ内容がなぜ違うのかを**開発側から**説明する。
   - **この説明を「正解」として覚えさせない。**
4. **2 回目の合同評価でずれが収まったことを確認したら訓練終了。**
   - 収まらない場合はルーブリックの文言が曖昧なので、**文言を書き直してから
     訓練し直す**（評価を始める前に直す）。

## 5. 結果の記録

結果は **`eval/results/YYYYMM.json`**（月ごと 1 ファイル）に保存する。

```json
{
  "schema_version": 1,
  "period": "202610",
  "rubric_version": 1,
  "raters": ["A", "B", "C"],
  "conditions": {
    "baseline": "現行プロンプト",
    "candidate": "変更後プロンプト"
  },
  "sessions": [
    {
      "rater": "A",
      "cases": [
        {
          "case_id": "care_recreation-1975",
          "presented_order": ["A", "B"],
          "axis1_nostalgic_natural": "A",
          "axis2_conversation_prompting": "B",
          "axis3_has_error": "B"
        }
      ]
    }
  ],
  "notes": "自由記述。行事の都合など、施設ごとの事情はここに書く。"
}
```

### 読むべき数値

| 数値 | 定義 | 読み方 |
|---|---|---|
| **Best-Worst スコア** | 1 軸で baseline を最良と選んだ割合 − 最悪と選んだ割合 | −1 〜 +1。**月次トレンド**として読む |
| **誤り率** | 軸 3 で Yes と答えた割合 | **下げることが最優先**。上がったら検索へ戻す |
| **一致度** | 評価者どうしの選択が一致した割合 | **低いならルーブリックの訓練が足りない**。評価者の問題ではない |

> **n=3 で月 1 回の評価は、統計的な有意差を主張するには小さい。**
> したがって**月々の差を統計的に解釈してはならない**。
> 明显的（例: Best-Worst スコアが 2 か月連続で +0.3 以上）なときだけ
> 「効果の再現の可能性」を述べる程度にする。
> これは提案 450 行の「本アプリでの有効性は未検証」という判断の延長である。

## 6. 運用ルール（重要）

> ### ⚠️ プロンプトを変えるたびに 2 回以上回す

- プロンプトを 1 回変えただけで Best-Worst を 1 回しか回さないと、
  **提示順の効果とプロンプトの効果を分離できない**。
- したがって: **プロンプトの変更 1 件に対して、Best-Worst を最低 2 回
  （別セッション・別日）回す。**
- 2 回のうち 1 回は**提示順を全面的に入れ替える**。入れ替えても結果が変われば、
  それはプロンプトの効果ではなく**提示順の効果**なので比較に使わない。
- 1 つのプロンプト変更に対して**同じ評価者**を使う
  （評価者をまたぐと個人差と条件差が分離できなくなる）。

### その他のルール

- **評価中にルーブリックを変えない。**
- **評価中にプロンプトを変えない。**（セッション中で公平な比較ができない）
- 評価者ごとに**別々のファイル**に記録してから統合する
  （片方の評価者が他方の回答を見ないようにする）。
- 評価者が「わからない」を選んだ場合は**「どちらにもない」**として記録し、
  分析から除外しない。除外すると軽い方が勝つ。
